# p5.js — tuning

What each job taught the p5.js page. Each item names what the job showed and what changed because of it, if anything did. Newest last. These are the page's dated gotchas, moved here on 2026-11-08 when its Gotchas became present-tense rules. The page's `last_tested` date, the Shop harness's smoke on 2026-06-16, is kept as the first run line.

## From the two-phasor coupling explorer — 2026-05-10 — Sketch, the first job

1. **A background tab throttled `requestAnimationFrame` to about 1 Hz, and the simulation looked frozen.** With `dt = clamp(now - lastTime, 0.05)`, a Kuramoto-style integrator advanced only ~0.05 s of simulation time per second of wall-clock; to a programmatic browser driver or a screenshot flow that reads as a hung sketch. The clamp is right, guarding against a catastrophic first frame; the visible behaviour misleads. Changed: two mitigations named — drive the simulation off a `setInterval` timer when verification needs it, or say in the Sketch that focus is required. Sketch tier accepts the throttle as a known limit. Item 3 later set the timer aside for animated sketches.
2. **The first canvas under-used its vertical space.** At 1080×480, phasors at y=90 and the trace baseline at y=320 left ~70 px empty below the trace axis. Changed: cosmetic at Sketch; flagged for promotion — at Study or Piece, re-aspect the canvas or move readouts and labels into the unused band.

## From the Flocking expressive Sketch — 2026-05-29 — the second p5 job

3. **A headless harness paused `requestAnimationFrame` outright, not just throttled it.** In the Claude Preview static-server harness for [[Flocking]], rAF callbacks never fired (a probe counter stayed at 0). p5's `draw()` loop is rAF-driven, so the canvas showed only `setup()`'s background. Exposing the instance (`window.__flock = p` in `setup()`) and forcing frames with `__flock.redraw()` pumped 450 frames, and the flock rendered correctly. Changed: a sketch that must be verified headlessly gets a labelled redraw seam, not a `setInterval` loop, which would degrade trail smoothness on real tabs. The sibling [[Observable Plot]] sketch keeps `setInterval`, rightly: it is a slow analytical re-render, not smooth animation.
4. **Fading trails: veil, don't clear — confirmed again.** A low-alpha full-canvas `rect` each frame (`fill(h,s,b,14)` in HSB) left the fading trail; `background()` or `clear()` each frame destroys it. Trail length depends on framerate: the veil accumulates differently at 30 fps than at 60. Changed: nothing new beyond the note that trail length moves if a sketch goes to a fixed-rate timer.

## From the test scroll — 2026-11-15 — two probes: a WebGL field for mouse and finger, and the same sketch in p5 1.10.0 and 2.4.0

- run · 2026-11-15 · a lit WebGL field pressed by the mouse and by two fingers on an emulated phone (proofs/2026-11-15-webgl-touch), probe · taught item 5
- run · 2026-11-15 · zoom-out: one sketch in p5 1.10.0 and p5 2.4.0 side by side, a closed spline and a warp filter shader (proofs/2026-11-15-p5-1-vs-2), probe · taught items 6, 7, 8

5. **WebGL mode and touch held in p5 1.10.0, headless; `touch-action: none` on the canvas is what keeps the page still.** A lit field of 160 boxes in `WEBGL` came up as WebGL2 in Chromium headless (SwiftShader). The real mouse pressed the boxes under it (the warm pixels' centroid within 0.05 of the pointer, a fraction of the canvas); two fingers sent through Chrome's input pipeline (CDP `Input.dispatchTouchEvent`, a 390 x 844 phone emulated) were both in `p.touches` and pressed two places at once; the field sprang back when they lifted. A finger dragged on the field scrolled the page 0 px with `touch-action: none` on the canvas and 584 px without it; the same drag on text scrolled about 400 px, the control (404 on the last run). In 1.x p5's touch handlers listen on the whole window, so returning `false` from them to stop scrolling would also swallow taps on the page's own buttons; the CSS line does it without that. One tap fired `touchStarted`, `touchEnded` and one `mouseMoved` (the browser's compatibility mouse event), and not `mousePressed`. The field's first screenshot also left an empty band below it (item 2 again: the boxes' standing height pushed the drawing up); shifting the field down fixed it. Emulated only: no real phone or finger has touched it. Nothing changed on the page; owed a review.
6. **Under p5 2.x the redraw seam must be awaited.** In p5 2.4.0, `redraw()` is `async` and returns at once if a draw is still in flight, so a loop of 200 unawaited `redraw()` calls drew almost nothing and a screenshot after it read the frame before (measured 0 ms a frame and stale pixels, until the check awaited each one). `await p.redraw()` works in both versions (1.x returns nothing to wait for). The card's Checked by line and the starter's header say `window.__sketch.redraw()` with no await, true for 1.10.0. Nothing changed on the page; owed a review.
7. **p5 2.4.0 has two load-time surprises a piece will meet.** (a) As it loads, it fetches `./<navigator.language>.json` beside the page for its friendly-error translations, then `cdn.jsdelivr.net/npm/p5@2.4.0/translations/en-US/extracted.json`, which is a 404 (the package has `translations/en/`, not `en-US/`); unless localStorage already holds it, that is two console errors in every piece, which conform's browser pass counts against it. The proof answers the local fetch with an empty table for the moment the script loads, then puts `fetch` back; the English messages are built in. (b) 2.x registers itself onto any `window.p5` it finds, so loading it after 1.x threw ("Cannot set properties of undefined (setting 'presetup')") until the page captured 1.x and deleted `window.p5` between the two scripts. Both seen in Chromium headless on 2026-11-15; whether (a) is reported upstream was not searched. Nothing changed on the page; owed a review.
8. **Zoom out, tried: p5 2.4.0 against the shelf's 1.10.0.** npm registry, read 2026-11-15: `latest` is 2.4.0 (2026-11-11) and `r1` is 1.11.13, the 1.x line still kept. github.com/processing/p5.js/releases/tag/v2.4.0: WebGPU mode as an add-on (`p5.webgpu.js`, `await createCanvas(w, h, WEBGPU)`, falling back to WebGL when WebGPU fails), p5.strands shaders written in JavaScript (`buildFilterShader`, `buildMaterialShader`, marked experimental), SVG import and export built in, multi-material `loadModel()`, a spinning-star loading animation by default. github.com/processing/p5.js-compatibility (read 2026-11-15) lists what 1.x code must change: `preload()` gone for `async setup()` and `await`; `curveVertex` becomes `splineVertex` and `endShape(CLOSE)` closes smoothly; mouse and touch become one pointer API (`touches` instead of the touch handlers); `mouseButton` an object; `keyCode` against named constants no longer works; a shader applies to fills only; p5.sound replaced and incompatible. Tried: the same sketch (a closed curve leaning to the pointer, a warp filter shader) in both, one page. They drew within 0.06% of the same pixels at the same pointer, unwarped and warped, and the warp changed 4.1% of pixels in each. Forced frames in SwiftShader: 1.10.0 median 19.6 ms (p95 66.2), 2.4.0 median 3.0 ms (p95 18.3) — a comparison on a software GPU, not a speed on Loudon's Mac. Code that changed: the setup became async, `curveVertex` plus three repeated points became `splineVertex` plus `endShape(CLOSE)`, and the GLSL string became a strands function handed `{ p }` in instance mode. 2.4.0's `lib/p5.min.js` is 1,066,050 bytes (308,839 gzipped) against 1.10.0's 1,041,843 (247,984). Not tried: WebGPU mode, 1.11.13, p5.sound in 2.x. Whether the pin moves, and to which, is Loudon's call. Nothing changed on the page; owed a review.
