## From the Flocking shoot-out — 2026-05-29 — Reynolds boids, interactive-control lens, Sketch tier

1. **d3-force is a relaxation solver, not a kinematic integrator,** and that cut against the brief that named it the "primary lane." d3-force expects forces to add into `node.vx`/`node.vy` each tick, then damps velocity (`velocityDecay`) and cools (`alpha`) toward a settled layout. Reynolds boids keep velocity as persistent state, clamped to a maximum speed and never damped; the naive add-into-vx approach with default decay cooled to a frozen blob and would not match a hand-rolled loop. Changed: to reproduce the Reynolds Euler step exactly, so the three Specimens share one trajectory, `velocityDecay(0)`, `alphaDecay(0)` + `alphaMin(0)`, and a custom force that replaces velocity with the clamped result. Documented inline in the file header. For Reynolds, d3-force is a bare tick driver; the real D3 win is the selection, SVG and interaction grammar.
2. **Naming the steering fields `fx`/`fy` pinned every boid in place,** because d3-force reads them as fixed positions. Cost a confusing minute of frozen boids. Changed: the fields became `steerX`/`steerY`.
3. **Three accumulating forces (`forceSeparation`, `forceAlignment`, `forceCohesion`) broke the snapshot semantics:** d3 runs forces in order over all nodes, so alignment would read velocities separation had already changed that tick. Changed: one force that computes all new velocities from a frozen snapshot (pass 1), then writes them (pass 2).
4. **Wrapping only the position update left edge boids seeing too few neighbours,** and alignment broke at the seam. Changed: the minimum-image delta goes inside neighbour-finding too, and positions wrap in the `tick` handler after d3-force applies `x += vx`.
5. **The browser-pane harness used to verify [[Flocking]] never fired `requestAnimationFrame`,** so d3's timers stalled and the sim looked frozen; the files animated normally on a focused tab. Changed: verify by calling `d3.timerFlush()` in a loop to force synchronous ticks, through top-level `function` declarations a classic `<script>` makes global; read computed styles, not screenshots, for colours and fonts. The harness checks render, structure and tokens, not motion feel. This item came to the page on 2026-10-22, rehomed here when Surfaces and Capabilities went to compost (`a0c481a4`); it has not been rechecked since 2026-05-29.

## From the test scroll — 2026-11-15 — two probes: the Shop as a relaxed graph, and the whole library against the modules

- run · 2026-11-15 · the Shop as a relaxed graph: Shop pages' typed links, keyboard and screen-reader paths (proofs/2026-11-15-shop-graph), probe · taught items 6, 7, 8, 9
- run · 2026-11-15 · zoom-out: d3@7.9.0 whole script against the d3-force 3.0.1 and d3-selection 3.0.1 ES modules by import map (proofs/2026-11-15-esm-modules), probe · taught items 10, 11

6. **On palace data, two hubs knot the layout.** Nearly every Shop page links [[The Shop]] and the [[Maker]], so with every link at its default strength d3-force pulled the Shop into one knot round those two. Holding the links to any node of degree over 25 loose (strength 0.02, distance 200) and fading them let the Specialists settle by the links that tell them apart: the D3, Plot, p5, Tone neighbourhood and the ffmpeg, Whisper, Kokoro one show by eye in the screenshot. Edge crossings 7902 at the start, 1383 settled. A frame force (a clamp in the tick) kept a loose leaf in view. Nothing changed on the page; owed a review.
7. **d3-force is deterministic, so a harness can tick it rather than pump timers.** The Relax button (the simulation's own timer, 300 ticks) and `simulation.tick(300)` after a reset landed on the same positions to the bit, in Chromium 147 headless, and d3@7.9.0's d3-force and d3-force 3.0.1 land on the same positions as each other. For a relaxation, `tick(n)` is a cleaner check than item 5's `d3.timerFlush()` loop; item 5 still stands for motion. Nothing changed on the page; owed a review.
8. **A roving tabindex in an SVG: the `<svg>` itself took the first Tab.** The `<svg>` carried `role="group"` and an ARIA label, and Chromium 147 put it in the tab order ahead of the node holding `tabindex="0"`, so every arrow key landed nowhere. `tabindex="-1"` on the svg fixed it. Seen headless only, and which attribute made the svg focusable was not tested. Nothing changed on the page; owed a review.
9. **A declared file and the checker.** conform's browser pass frames a piece sandboxed with no origin, where the fetch of a declared `shop-graph.json` is refused (warned as sandbox-blocked); the same piece framed on the piece origin by its plan, as a scroll frames it, read the file and drew all 111 nodes (check.mjs). The piece says plainly in its status line when it cannot read the file. Nothing changed on the page; owed a review.
10. **Zoom out, tried: d3 now ships each module as one ES-module file.** github.com/d3/d3/releases, v7.9.1 (2026-11-03): "Publish an ES module bundle instead of separate source files"; v7.9.2 the same day reverts a d3-delaunay fix; d3-force 3.0.1, d3-selection 3.0.1 and the rest the same day (npm registry, read 2026-11-15). No new API: the change is how d3 is delivered. Tried: a force graph needs five module files, 9.3 KB compressed (28.9 KB parsed) against the whole script's 89.9 KB (273.2 KB), and drew the same positions to the bit. An import map's `integrity` pins each file, and Chromium 147 refused a module whose hash was wrong. Cold load time was not told apart in five loads a side (medians 343 and 370 ms on one run, 950 and 368 on another; the CDN's noise is larger than the difference). The shelf has none of the five URLs yet. Nothing changed on the page; owed a review.
11. **Import maps and the Shop's checks.** conform reads an import map's URLs and hashes (so the five module URLs show as off-shelf until the shelf has them) but reads a bare import name such as `'d3-force'` as a file beside the piece, so the page imports its two top modules by full URL and the map resolves only the names d3-force imports itself. `Shop/Maker/web-smoke.mjs` parses a `<script type="importmap">` as classic JavaScript and fails it ("Unexpected token ':'"); a one-line filter on the script's type would fix it. Not fixed here; owed a review.
